## 3. `POST /api/chat` 详细设计

### 3.1 请求

```json
{
  "session_id": "sess_7f3a1c",     // 可选；为空则由服务端新建会话并在首个事件回传
  "question":   "智能门锁指纹识别无响应怎么办？",
  "user_id":    "demo_user"        // 可选，默认 demo_user
}
```

### 3.2 响应：SSE 事件流（`Content-Type: text/event-stream`）

一次成功问答的事件时序：

```
event: session      → {"session_id":"sess_7f3a1c"}         会话已就绪（新建时才有）
event: status       → {"stage":"retrieving","text":"正在检索制度…"}
event: citations    → {"items":[ ... 引用对象数组 ... ]}     检索完成，先把依据推给前端
event: status       → {"stage":"generating","text":"正在生成回答…"}
event: delta        → {"text":"【结论】"}                    逐块文本，前端直接追加
event: delta        → {"text":"可能是指纹头脏污…"}
        ... （N 条）
event: done         → {"message_id":42,"model":"deepseek-chat",
                       "usage":{"prompt_tokens":..,"completion_tokens":..},
                       "latency_ms":1830,"degraded":false}
```

事件说明：

| 事件 | 时机 | 载荷 |
|---|---|---|
| `session` | 首轮（前端未带 session_id） | `{session_id}` |
| `status` | 阶段切换 | `{stage, text}`，前端用作状态条文案 |
| `citations` | 检索完成后立刻推送 | 引用对象数组（见 §7） |
| `delta` | 模型流式输出 | `{text}` |
| `error` | 流**已开始之后**出错 | `{code, message}` |
| `done` | 正常结束 | `{message_id, model, usage, latency_ms, degraded}` |

为什么 `citations` 要单独一个事件、而不是塞进 `done`：
前端需要在**答案还没生成完**时就把"依据"渲染出来，用户能边看答案边对照原文，这是溯源体验的关键；
同时它也是"检索已完成"的信号，状态条可以从"正在检索制度…"切到"正在生成回答…"。

### 3.3 两个必须提前讲清楚的工程约束

**（1）前端不能用 `EventSource`，必须用 `fetch` + `ReadableStream`**

`EventSource` 只支持 GET，而 `/chat` 是 POST（问题可能很长，放 query string 不安全也不优雅）。
所以前端用 `fetch` 拿 `response.body.getReader()`，按 `\n\n` 手撕 SSE 帧——这部分我会封装成一个约 40 行的 `readSSE()` 函数。
附带好处：可以带 `AbortController` 实现"停止生成"按钮。

**（2）SSE 一旦开始，HTTP 状态码就改不了了 → 错误必须分层处理**

所以设计上把错误切成两段：

- **前置校验（同步完成，失败直接返回 HTTP 4xx/5xx + 统一 JSON）**
  参数缺失/超长、session_id 不存在、知识库未就绪。这些都是"本地能 100% 判定"的，绝不带进流里。
- **运行时错误（流已开始，只能发 `error` 事件）**
  Embedding 调用失败、大模型超时/额度不足。此时前端收到 `error` 事件 → 展示中文错误 → **并自动切降级模式**（把召回原文直接展示，保证用户永远拿得到东西）。

这是"所有接口先返回错误码和中文错误信息"这条约束在流式场景下的唯一正确落地方式，很多实现在这里做错（先 200 再报错，前端永远收不到）。

## 4. 统一错误码

全部接口统一返回结构：

```json
{ "code": 1001, "message": "问题不能为空", "data": null, "trace_id": "b3f1c9" }
```

| 区间 | 含义 | HTTP |
|---|---|---|
| `0` | 成功 | 200 |
| `1xxx` | 参数/校验错误 | 400 / 422 |
| `2xxx` | 会话错误 | 404 / 409 |
| `3xxx` | 知识库与检索错误 | 503 |
| `4xxx` | 大模型调用错误 | 502 / 504 |
| `5xxx` | 系统内部错误 | 500 |

| code | message（中文） | HTTP | 触发条件 |
|---|---|---|---|
| 0 | 成功 | 200 | — |
| 1001 | 问题不能为空 | 400 | `question` 空或纯空白 |
| 1002 | 问题长度超限（最多 500 字） | 400 | 超长 |
| 1003 | 请求参数格式不正确 | 422 | Pydantic 校验失败 |
| 2001 | 会话不存在或已被删除 | 404 | `session_id` 查不到 |
| 2002 | 会话不属于当前用户 | 403 | `user_id` 不匹配 |
| 3001 | 知识库尚未就绪，请稍后重试 | 503 | 启动时索引构建失败 |
| 3002 | 检索失败，未命中任何制度条文 | 200* | 命中为空（*不报错，走"知识库未覆盖"话术） |
| 3003 | 知识库文件不存在 | 503 | `data/售后知识库.md` 丢失 |
| 4001 | 大模型调用失败，已切换降级模式 | 200* | 网络/额度异常（*流内 error 事件，随后降级输出） |
| 4002 | 大模型响应超时 | 504 | 超过 60s 无首字 |
| 5001 | 服务内部错误，请联系管理员 | 500 | 未捕获异常 |

> `3002` 和 `4001` 刻意**不算失败**：前者是知识库边界（应如实说"未覆盖"），后者是外部依赖故障（应降级而非报错）。把这两类当错误抛给前端，是 RAG 系统最常见的体验事故。

## 5. 数据库表（SQLite）

沿用架构方案里的 `sessions` / `messages`，裁剪为 SQLite（`INTEGER PRIMARY KEY` + `TEXT` 存时间 + JSON 存字符串）。

```sql
-- 会话表：一次"连续对话"一行
CREATE TABLE IF NOT EXISTS sessions (
    id            TEXT PRIMARY KEY,        -- 'sess_' + 16 位十六进制
    user_id       TEXT NOT NULL DEFAULT 'demo_user',  -- 预留，阶段3 接登录
    title         TEXT NOT NULL DEFAULT '新对话',      -- 取首条问题前 20 字
    message_count INTEGER NOT NULL DEFAULT 0,
    created_at    TEXT NOT NULL,           -- ISO8601，统一 UTC+8
    updated_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_sessions_user ON sessions(user_id, updated_at DESC);

-- 消息表：一问一答各一行（role = user / assistant）
CREATE TABLE IF NOT EXISTS messages (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id    TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
    role          TEXT NOT NULL CHECK(role IN ('user','assistant','system')),
    content       TEXT NOT NULL,           -- 正文
    citations     TEXT,                    -- JSON 数组（仅 assistant）：引用来源
    chunk_ids     TEXT,                    -- JSON 数组：命中的切片 id，用于复盘检索质量
    model         TEXT,                    -- 实际模型名；降级时为 'local-fallback'
    degraded      INTEGER NOT NULL DEFAULT 0,   -- 1 = 降级输出（未走大模型）
    prompt_tokens INTEGER DEFAULT 0,
    completion_tokens INTEGER DEFAULT 0,
    latency_ms    INTEGER DEFAULT 0,       -- 端到端耗时，含检索
    created_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_messages_session ON messages(session_id, id);
```

**与阶段 1 `Chunk` 的对应关系**（说明"沿用"到底沿用了什么）：

| 阶段 1 | 阶段 2 |
|---|---|
| `Chunk.id` | `messages.chunk_ids` 里的元素 |
| `Chunk.heading` | `citations[].heading` |
| `Chunk.text`（截断 200 字） | `citations[].snippet` |
| `hybrid_search` 的融合得分 | `citations[].score` |
| `Answer.usage` / `model` / `degraded` | `messages` 同名列 |

**为什么 SQLite 用同步 `sqlite3` + 线程池，不引 aiosqlite：**
本阶段写入量极小（每轮 2 行），同步驱动配 `run_in_threadpool` 完全够用，少一个依赖、少一个心智负担。阶段 3 换 PostgreSQL 时，把 `db.py` 换成 `asyncpg` 即可，上层无感。

## 6. 历史上下文策略（最近 6 轮）

```
取该 session 最近 12 条消息（6 轮 = 6 问 6 答），按 id 升序拼进 messages 数组
```

三条细节（都是踩过的坑）：

1. **只取已完成的轮次**：若最后一条是 assistant 且生成中断（`degraded` 或异常），该轮不进上下文，避免把残缺答案喂回去。
2. **引用不进上下文**：历史消息只带 `content`，不带 `citations`。引用片段平均 200 字 × 6 轮 = 2400 字纯浪费。
3. **长度兜底**：单条历史超过 800 字则截断（保留开头 500 + 结尾 300），并在末尾加 `…（已截断）`。防止极端情况把上下文窗口撑爆。

最终 messages 顺序：`system`（护栏提示词）→ 历史 12 条 → `user`（含本轮检索到的参考资料）。

> 注意：参考资料**只挂在本轮 user 消息上**，历史轮次的参考资料不重复携带——否则第 6 轮的 prompt 会带上前 5 轮的全部片段，token 直接翻 5 倍。

## 7. 引用对象（citations）结构

前端底部展示"文件名 + 片段"，后端按此结构下发：

```json
{
  "index": 1,                                  // 对应答案里的 [1]
  "file": "售后知识库.md",                      // 来源文件名
  "heading": "三、智能门锁常见故障与处理",        // 所属章节
  "snippet": "指纹识别无响应：先用干燥软布擦拭…",  // 片段前 200 字
  "score": 0.0321,                             // RRF 融合得分，供调试
  "vector_rank": 1,                            // 向量通道排名（可选展示）
  "bm25_rank": 3                               // 关键词通道排名（可选展示）
}
```

`file` 取自 `settings.doc_path.name`，**不改动阶段 1 的 `Chunk` 类**（避免动到已验证过的代码）。
阶段 3 支持多文档后，这里自然扩展为 `doc_id` + `version` + `effective_from`。

## 8. 前端设计（`server/web/index.html`，单文件零依赖）

**布局**：顶部标题栏 → 中间消息流（气泡，用户右/助手左）→ 底部输入框 + 发送/停止按钮。

**关键行为：**

| 需求 | 实现 |
|---|---|
| 打字机效果 | 收到 `delta` 直接 `textContent +=`，天然就是打字机；若模型不支持流式（降级模式），前端按句切分 + 25ms 定时器模拟 |
| "正在检索制度…"状态 | 收到 `status` 事件 → 在助手气泡上方渲染一条带旋转动画的状态条；收到 `citations` 后改为"已找到 N 条依据"；收到首个 `delta` 后隐藏 |
| 引用来源 | 答案气泡底部渲染可折叠卡片区：每条显示 `[1] 售后知识库.md · 三、智能门锁常见故障与处理`，点击展开全文片段 |
| 错误展示 | `code != 0` → 红色错误气泡，显示中文 `message`；流内 `error` 事件 → 黄色提示条 + 随后展示降级原文 |
| 会话保持 | `session_id` 存 `localStorage`，刷新后自动 `GET /api/sessions/{id}/messages` 恢复历史 |
| 停止生成 | `AbortController.abort()`，前端停止渲染并提示"已停止"（后端随之结束生成器） |
| 快捷提问 | 底部 3 个示例问题按钮，方便答辩演示 |

**不做**：Markdown 渲染引擎（用极简规则处理 `【】` 分段与换行）、多会话侧边栏、移动端适配（仅做基本响应式）。

## 9. 关键取舍与风险

| 决策 | 取舍理由 | 风险/代价 |
|---|---|---|
| 用 `AsyncOpenAI` 做流式 | 阶段 1 是同步 client；流式用异步 client 最干净 | `llm_chat()` 与 `llm_chat_stream()` 会共存两份配置读取逻辑 → 我会抽公共 `_build_client_kwargs()`，避免双份 |
| 无 Key 时前端也要有打字机 | 降级答案按句切分 + 定时推送 `delta` | 演示效果好，但注释必须写清"这是模拟流式，不是真实 token 流" |
| 索引在应用启动时构建 | 复用阶段 1 的 `prepare()`，一次开销约 1~3s | 启动期间 `/api/health` 返回未就绪，前端需轮询；我会让 `/` 页面在初始化时先打 health |
| SQLite 单文件放在项目根 `data/chat.db` | 便于一起提交/备份 | 需在 `.gitignore` 里排除，否则每次运行都产生 diff |
| 检索放在流内而非前置 | 让前端能真实展示"正在检索" | 检索失败只能走流内 `error`；但已配降级路径，可接受 |
